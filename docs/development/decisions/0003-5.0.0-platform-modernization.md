# ADR 0003 — 5.0.0 platform modernization

**Status:** accepted

## Context

v4.7.2 targeted `sanity ^4 || ^5` with `@sanity/ui` v2 as a direct dependency, a legacy dual CJS/ESM build
(a `lib/` with stray `index.esm.esm.js` / `index.esm.d.mts` artifacts), `release-please` plus manual `npm
publish`, and a Sanity Studio-v1/v2 incompatibility shim. The rebuild bundled the sanctioned platform
breaking changes into a single **5.0.0** major.

## Decision

### Peers: `sanity ^5 || ^6`, `@sanity/ui` v3, `styled-components` — all peers

The key finding: **Sanity 4, 5, and 6 all bundle `@sanity/ui` v3** (5.0 → `^3.1.11`, 6.1 → `^3.2.0`). The
plugin's `@sanity/ui: ^2.8.9` dependency was simply **stale** — the dev studio had been deduping the
plugin's `@sanity/ui` imports to the studio's v3 at runtime all along, which is why everything rendered.
So the "v2 → v3 migration" was a *dependency-declaration fix, with zero component changes* — the primitives
the plugin uses (`Box`, `Stack`, `Text`, `Button`, `Card`, `Dialog`, `Badge`, `Tooltip`, …) are identical
across v2 → v3.

- `@sanity/ui` and `styled-components` move from **dependencies to peer dependencies** (the host studio
  provides them; this also avoids duplicate copies, the real footgun). The plugin imports neither
  `styled-components` directly nor any v2-only `@sanity/ui` API.
- `sanity` peer: `^4 || ^5` → **`^5 || ^6`**.
- `react` / `react-dom` peers tightened to **`^19`** (Sanity 5/6 require React 19).

### Sanity 6 support

The dev studio flips to Sanity 6. Exactly **one code change** was needed: `sanity-plugin-utils` v2 retyped
`useListeningQuery`'s return, so `views/ConceptUseView` parameterizes its query with `TagReference[]` and
drops a now-redundant cast. `sanity-plugin-utils` → **^2** (its peer range includes Sanity 6); it is
**bundled into the plugin output** (a devDep that pkg-utils inlines), so updating it keeps the bundled
`useListeningQuery` Sanity-6-compatible.

> Re-verify the `@sanity/ui` / `sanity-plugin-utils` compatibility whenever widening the `sanity` peer
> range — the v2→v3 "non-event" was specific to the dedupe situation above; a future major (v7+) needs its
> own check.

### ESM-only `dist/`

`pkg-utils` with `legacyExports: false` + `"type": "module"` emits a single clean entry
(`dist/index.js` + `.d.ts` + map) — no more stray dual-format files. `exports["."]` is `source` / `import`
/ `default` → `./dist/index.js`; the CJS `require` condition and the legacy `module` field are dropped.

### Drop the Studio-v1/v2 shim

`sanity.json` + `v2-incompatible.js` (+ the `@sanity/incompatible-plugin` dependency) only ever did
anything inside a pre-v3 Studio (an "upgrade this plugin" dialog). They're dead weight for a `sanity ^5 ||
^6` package, and `v2-incompatible.js`'s CJS `require()` is incongruous under `"type": "module"` — removed.

### Release: `release-please` → `semantic-release` + OIDC

`.releaserc.json` extends **`@sanity/semantic-release-preset`** (the canonical Sanity-plugin config:
commit-analyzer with conventionalcommits, release-notes, changelog, npm, github, git, license).
`.github/workflows/release.yml` runs on push to `main` (+ manual dispatch) and publishes via **OIDC
trusted publishing** — `id-token: write`, provenance, **no `NPM_TOKEN`**. The version is computed from
Conventional Commits; the four `BREAKING CHANGE` commits since `v4.7.2` make the first automated release
**5.0.0**.

- **The studio is intentionally outside the gate** (eslint-ignored; not in typecheck/build/test).
  `pnpm --filter studio build` is the headless integration check that the plugin composes into a Sanity 6
  studio.
- **OIDC caveat:** publishing requires the package to be configured as a **trusted publisher** on
  npmjs.com (pointing at this repo + `release.yml`). If the bundled `@semantic-release/npm` can't do
  tokenless OIDC, the fallback is an `NPM_TOKEN` secret + env — noted in `release.yml`.

## Consequences

- 5.0.0 is **ESM-only**, targets **`sanity ^5 || ^6` / `@sanity/ui` v3 / React 19**, and releases
  automatically on merge to `main`.
- Local `semantic-release --dry-run` can't fully verify the version until the commits are on `main` (it
  requires the release branch on the remote); the first real release runs in CI after merge.
- Never `npm publish` by hand, never hand-edit `CHANGELOG.md`, and never squash/rebase `main` (see
  [CLAUDE.md](../../../CLAUDE.md) — semantic-release reads every commit).
